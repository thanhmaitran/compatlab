# CompatLab Technical Report

## 1. Executive Summary
CompatLab compares two versions of an OpenAPI specification, classifies every difference as BREAKING, NON_BREAKING or CONDITIONAL separately for backward and forward compatibility, determines which registered consumers are affected, generates and runs tests on a mock, and enforces a release policy in CI/CD. A dashboard and a REST API expose the same engine.

## 2. Problem Statement
API changes that look small in a textual diff (for example `integer` to `string`) break consumers. Teams need an automated, explainable and reproducible check before release.

## 3. Objectives
Deterministic semantic diff; explainable rules with remediation; consumer-aware impact; bounded, safe test execution; policy-as-code; history and trends; measurable quality.

## 4. System Requirements
Functional requirements are the modules in [component architecture](../architecture/component-architecture.md). Non-functional: reproducible output, input limits, tenant isolation, no execution against unlisted targets, no secrets in logs or recordings.

## 5. Related Technical Concepts
Semantic versioning and API evolution; backward/forward compatibility; consumer-driven contracts (Pact-style ideas, own implementation); property/boundary testing (Schemathesis-style ideas, own implementation).

## 12. Security Considerations
Untrusted specification input (size/depth limits, alias-bomb protection, no external references); target allowlist and connect-time address guard; masked recordings; bcrypt and pinned-algorithm tokens; tenant isolation; rate and size limits; parameterized SQL (checked by a static test); generic 500 responses. See ADR-0004 and `tests/security`.
